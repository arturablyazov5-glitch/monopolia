# Правила работы над проектом «Монополия»

## Основные правила

- Исправлять корень проблемы: находить и менять исходное правило, разметку или источник данных. Не накапливать компенсирующие отступы и CSS-переопределения; удалять неудачные заплатки и дублирующие правила.
- Одинаковые элементы должны использовать общий класс и, когда повторяется разметка или поведение, общий компонент. Стили и поведение задавать в одном месте, чтобы исправление применялось ко всем экземплярам на всех страницах. Различия задавать явными вариантами только при реальной необходимости.
- Сохранять готовую вёрстку, существующие взаимодействия и общие компоненты. Не начинать с нуля.
- Перед исправлением общего компонента найти все места его использования и варианты (например, buy/sell). Если правка не ограничена пользователем одной страницей, применять её ко всем соответствующим вариантам. Проверять результат на каждой затронутой странице; для кнопок попапов — реально нажать кнопку и проверить, какая форма открылась. Не считать проверку одного варианта проверкой всего компонента.
- Соблюдать область правки: изменения только для мобильных ограничивать соответствующим media query; исключения для одного элемента не распространять на остальные.
- Не пушить, не публиковать и не подключать реальные отправки заявок без разрешения пользователя.
- Не запускать дополнительных агентов без явного разрешения пользователя.
- Не придумывать отсутствующие тексты, кейсы, сотрудников, видео, документы или ссылки.

## Стек и структура

Astro + TypeScript + обычный CSS. Не добавлять React, Tailwind или лишние библиотеки.

- `src/pages/index.astro`, `sell.astro`, `buy.astro` — основные страницы.
- `src/components/` — общие элементы и секции; перед созданием нового искать существующий.
- `src/styles/tokens.css` — общие токены; `global.css` — общие стили; остальные файлы — стили компонентов и секций.
- `src/layouts/SiteLayout.astro` — общий каркас. Footer подключается здесь, не дублировать на страницах.
- `src/data/` — данные и тексты; использовать существующие источники.
- `public/assets/` — локальные ресурсы.
- `design-reference/original-assets/` — исходные экспорты до оптимизации.
- `PROJECT_MEMORY.md`, `UI_KIT.md`, `design-reference/` — история решений, библиотека и материалы проверок. Исторические статусы проверять по текущему коду.

Использовать существующие локальные шрифты и токены, не подключать их повторно.

## Поддержка архитектуры

- Перед изменением проследить цепочку: страница → компонент → общие примитивы → стили и обработчики → ресурсы. Найти все действующие правила для проблемного элемента, включая адаптивные файлы и порядок их подключения. Сначала подтвердить причину дефекта, затем менять код; предположение не выдавать за установленную причину.
- У каждого элемента и поведения должен быть явный владелец. Страница собирает секции и передает данные/варианты; компонент задает собственную разметку и поведение; общий примитив задает повторяемое оформление. Не копировать реализации между страницами и не создавать второй обработчик уже существующего взаимодействия.
- `tokens.css` хранит общие значения, `global.css` — базовые правила и действительно общие примитивы, файл компонента — его оформление и адаптив. Не добавлять в `global.css` исключение для одной секции. При работе со старыми общими адаптивными файлами переносить затронутые правила к владельцу вместе с удалением прежних определений, проверяя порядок каскада.
- Менять исходное правило, а не дописывать очередной селектор в конец файла. Удалять отмененные решения и дубли. Не повышать специфичность, не добавлять `!important`, отрицательный отступ, дополнительную полоску или перекрытие только ради сокрытия непонятного дефекта. Геометрические нахлесты из дизайна сохранять и описывать по назначению.
- Общие варианты задавать через props, классы варианта и CSS-переменные. Исключение для продажи, покупки или мобильного состояния должно быть явным и ограниченным этим вариантом. Не менять назначение общего компонента ради одной кнопки; использовать подходящий существующий примитив.
- Объединять элементы в общий компонент по совпадению ответственности и поведения, а не только внешнего вида. Не вводить универсальную абстракцию, библиотеку или массовую миграцию ради локального исправления. При реорганизации сохранять публичные варианты и проверять всех потребителей.

### Фоны, бумага и рваные края

- У каждой видимой кромки должен быть один ответственный слой. Не накладывать на один стык рваный SVG, маску всей секции и дополнительную маскированную полоску. Если слои нужны по дизайну, явно разделить их назначение: фон, текстура, край, тень, контент.
- Декоративные маски и фильтры по возможности применять к слою краски, а не к контейнеру с текстом, полями и раскрывающимися меню. Проверять создаваемые `mask`, `filter`, `transform`, `isolation` и `z-index` контексты наложения: высокий `z-index` потомка не выводит его из контекста родителя.
- Структурный фон, обеспечивающий цвет и читаемость секции, не должен появляться только после ленивой загрузки декоративного изображения. Отделять основу поверхности от текстуры и фотографий; проверять медленную загрузку, ошибки ресурса и прямой вход по якорю. Не переводить все изображения в eager без разбора.
- Сохранять пропорции фотографий. Масштабирование интерфейса через `zoom`, принудительный GPU-слой, `will-change`, размытие или однопиксельное перекрытие не считать исправлением без подтвержденной причины. Для нечеткого края сначала проверить исходный ресурс, alpha-канал и фактический масштаб.

### Навигация и диалоги

- У перехода по якорю должен быть один управляющий сценарий. Учитывать закрытие меню, восстановление прокрутки, готовность шрифтов и структурного фона до измерения цели. Не допускать конкурирующих нативного перехода, `hashchange`, `load` и программной прокрутки. Сохранять согласованную плавность; учитывать `prefers-reduced-motion`.
- Диалог отвечает за модальность на протяжении открытия и закрытия: фон не получает взаимодействия и не прокручивается, внутреннее содержимое прокручивается, позиция страницы и фокус возвращаются без скачка. Проверять вложенные списки, повторное открытие и закрытие во время анимации. Повторяющуюся механику блокировки и восстановления поддерживать в одном общем модуле при ее изменении в нескольких владельцах.

### Завершение архитектурной правки

- Проверять не только исправленный фрагмент, но и его границы с соседними секциями, все затронутые варианты и состояния. Для мобильных дефектов Safari использовать WebKit; проверять дробные координаты и плотность экрана, когда дефект связан со швом или мерцанием. Сохранять проверку desktop, если менялся общий источник.
- Если ошибка возникает только после публикации, сравнить фактически отданные HTML/CSS/JS и ресурсы с локальными, включая результат `scripts/prepare-pages.mjs`. Не компенсировать повреждение публикации стилями компонента.
- Перед завершением просмотреть итоговый diff: нет ли дублирующих правил, забытых компенсаций, изменений вне задачи и нарушения общих вариантов. Чужие параллельные изменения сохранять. После последней значимой правки повторить относящуюся к ней проверку.
- В результате отдельно указывать, что изменено, что реально проверено и где: локально или после публикации. Исправление одного узла не называть рефакторингом всей архитектуры; непроверенный сценарий или устройство обозначать прямо.

## Имена ресурсов

- Фотографии, иконки, фоны и декор именовать по содержимому и назначению, в нижнем регистре через дефис. Не оставлять случайные имена экспорта Figma и номера узлов вместо понятных названий.
- Портреты: `staff-имя-фамилия`; отдельные тени: `-shadow`; мобильные версии: `-mobile`; варианты по ширине: `-320w`, `-560w` и т. п. Не дублировать общий ресурс для разных страниц.
- При переименовании обновлять все ссылки, программно собираемые пути и реестр `src/lib/image-size.ts`; проверять загрузку изображений на всех затронутых страницах.
- Схема именования — `design-reference/asset-naming.md`, таблица выполненных переименований — `design-reference/asset-renames.json`. Исторические оригиналы и свидетельства проверок не переименовывать автоматически.

## Проверка

- Форматировать только изменённые файлы.
- `npm run check` — диагностика Astro/TypeScript.
- `npm run dev` — локальный сервер; точный адрес брать из вывода запуска и проверять, что он обслуживает этот проект.
- Визуальные изменения проверять в браузере на затронутых ширинах и страницах, включая окружающий интерфейс и состояния взаимодействия. Проверка исходников и успешная сборка не подтверждают внешний вид.
- При изменении поведения проверять соответствующие сценарии, в том числе ошибки валидации.
- После больших изменений геометрии запускать `node scripts/check-baseline.mjs`; данные в `design-reference/baseline-1440.json` сверять с текущими решениями пользователя, не восстанавливать устаревшую геометрию вопреки им.
- Сборку запускать, когда она нужна для задачи. Для работы с кейсами отдельное ограничение пользователя: не запускать `npm run build` без запроса.
- Не заявлять о публикации, отправке заявки или браузерной проверке, если они не выполнялись.
